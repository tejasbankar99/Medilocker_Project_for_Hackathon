## 2. Threat Modeling & Security Architecture

MediLocker follows a **Zero-Trust Security Model** across all client and backend tiers:

### 2.1 Database Security — PostgreSQL Row-Level Security (RLS)
- **Zero Client Bypass:** Direct database mutations through the Supabase client are constrained by PostgreSQL Row-Level Security policies evaluated inside the database engine.
- **Patient Data Sovereignty:** Patients can only read, insert, and delete documents where `user_id = auth.uid()`.
- **Scoped Doctor Access:** Physicians can query medical records ONLY when an active, non-expired, non-revoked row exists in `consent_grants` matching `doctor_id = auth.uid()` and `patient_id = target_patient_id`.

### 2.2 Dual-Factor OTP Consent Engine
- Access approval requires an ephemeral 6-digit cryptographic OTP generated by an isolated Deno Edge Function (`generate-otp`).
- Tokens expire in 10 minutes and self-invalidate upon first use (`is_used = true`).

### 2.3 Storage Security
- Medical documents uploaded to Supabase Storage reside in encrypted private buckets.
- File retrieval requires ephemeral time-bounded signed URLs generated by authenticated doctor sessions after verifying active consent.

### 2.4 Immutable Audit Logging
- Security events (`consent_requested`, `consent_approved`, `consent_revoked`, `document_viewed`) are appended to an immutable `audit_logs` table with no client-side `UPDATE` or `DELETE` grants.

## 3. Reporting a Vulnerability

If you discover a potential security vulnerability within MediLocker:
1. Please report vulnerabilities privately by emailing **security@medilocker.dev** or creating a private security advisory on GitHub.
2. Include reproduction steps, sample payload, and environment details.
3. The core engineering team acknowledges reports within 24 hours and provides remediation timelines within 72 hours.
